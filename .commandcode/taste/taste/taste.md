# Taste
- Is cost/token-conscious: wants the agent to avoid unnecessary token spend and not redo work already completed in a prior session — prefers resuming from the last known state (e.g., the exact file/line where a previous session stopped) before taking any further action. Confidence: 0.65
- Works under a limited agent/usage budget and wants minimal, surgical changes: reuse existing components, styling and architecture, don't refactor unrelated code, don't add unnecessary packages, and don't create unnecessary documentation. Confidence: 0.8
- Expects the agent to inspect the existing project structure and current implementation before making changes, and to never rebuild working features from scratch. Confidence: 0.75
- Prefers implementation over narration: explicitly doesn't want the agent spending time explaining what it is going to do up front, and dislikes agents that stall/get stuck. Wants a concise structured summary at the end rather than a long explanation. Confidence: 0.7
- After making changes, wants the agent to run the project's existing build/type-check command and fix any errors its changes introduced before finishing. Confidence: 0.65
- Wants large scopes broken into chunks and completed one at a time (with a visible plan/todo), rather than attempting everything in a single pass. Confidence: 0.8
- Design taste: wants a soft, clean, professional enterprise-SaaS look with restrained color use (light + dark mode). Dislikes harsh/over-saturated color combinations ("eye-blocking"), heavy gradients, excessive glassmorphism, oversized rounded cards, and over-animation. Confidence: 0.75
- Architecture preference: pages/components should read from a service layer instead of hardcoding data in components, so mock services can later be swapped for real APIs; Server Components by default with Client Components only where interaction/state is needed; no Redux (plain React state, context, localStorage, URL state). Confidence: 0.65
- Expects responsive layouts to be designed intentionally per breakpoint (mobile drawer nav, list → thread → detail panes) rather than a shrunken desktop layout. Confidence: 0.6
- Prefers messaging/inbox interfaces to feel like a real chat app (list rail + thread, conversation-focused) and to offer a full-screen immersive chat mode. Confidence: 0.6
- Wants chat UIs to mirror familiar consumer messaging conventions (e.g. Facebook Messenger): inbound/customer messages on the left, outbound/support messages (both AI and human agent) clearly on the right, plus read/delivery "seen" ticks — legibility of who sent what matters more than uniform styling; dislikes both sides rendering in the same style/position. Confidence: 0.7
- Likes color-coded status badges (each status with its own background color/icon) displayed as a small badge beside the customer/profile name, and expects such statuses to be editable from the UI (e.g. an order-status control in the customer details panel) with the badge updating live. Confidence: 0.6
- Performance-first for public-facing/marketing pages: cares about load speed and interaction smoothness, and expects library/tool choices to respect that — prefers lightweight, tree-shakeable options over heavy ones (e.g., avoid three.js/WebGL on a landing page), lazy-load heavy pieces, and honor reduced-motion. Confidence: 0.65
- Wants landing/marketing pages to sell the whole product through a realistic, story-driven example (a concrete end-to-end scenario the visitor can "imagine the entire system" from), not just feature lists. Confidence: 0.6
